description: Connect an MCP client to Starholder over Streamable HTTP, by signing in with OAuth or with your API key.

The **Model Context Protocol (MCP)** lets an AI agent discover tools and call them without hand-written HTTP code. Starholder runs an MCP server at `POST /api/v1/mcp`. Every tool runs as your API key, or as the connection key that approving an OAuth client creates ([Authentication](/docs/authentication#oauth-connection-mcp-clients)): it calls the same `/api/v1` route you could call yourself, and that route checks the call again. A tool can do exactly what the route allows that key to do, and nothing more.

## Connecting

```text
URL:        https://www.starholder.xyz/api/v1/mcp
Transport:  Streamable HTTP (JSON responses)
Auth:       OAuth sign-in (Authorization: Bearer <accessToken>),
            or X-Api-Key: <apiKey>   or   Authorization: Bearer <apiKey>
Protocol:   2025-06-18, 2025-03-26, or 2024-11-05
```

### Claude, ChatGPT, and other OAuth clients

Add Starholder as a remote MCP server with the URL above and OAuth as its authentication. Leave any client ID or secret fields empty: the client reads Starholder's sign-in settings from the server and identifies itself with its own published client metadata.

- **Claude:** Settings → Connectors → Add custom connector. Enter a name and the URL; Claude detects OAuth sign-in and its published identity. Choose **Add**, then **Connect**.
- **ChatGPT:** Plugins → Add → Add custom MCP server. Enter a name and the URL, with OAuth authentication; ChatGPT discovers the endpoints and uses its Client Identifier Metadata Document. Choose **Create as a plugin**, then **Continue to Starholder**.

Either way, the client opens Starholder in your browser. Sign in if asked, review the permissions, optionally choose **Read only**, and choose **Allow**. The connection then appears in Settings → API keys under **Connected apps**, where **Disconnect** ends it. Any MCP client that supports OAuth connects the same way, including native clients that receive the callback on a local port; [OAuth for MCP Clients](/docs/authentication#oauth-for-mcp-clients) has the protocol.

### With an API key

Clients that accept a custom header can send a key instead. For example, in a client that reads an `mcpServers` config:

```json
{
  "mcpServers": {
    "starholder": {
      "url": "https://www.starholder.xyz/api/v1/mcp",
      "headers": { "X-Api-Key": "YOUR_API_KEY" }
    }
  }
}
```

Or call it directly:

```bash
curl https://www.starholder.xyz/api/v1/mcp \
  -H "X-Api-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0"}}}'
```

The server is stateless. It issues no session id, and every HTTP request is authenticated on its own, so a revoked key or a disconnected app stops working on its next request. Authentication failures are HTTP errors, not JSON-RPC messages. A request without a credential gets `401` with `{ "error": "unauthorized" }` and a `WWW-Authenticate` challenge whose `resource_metadata` points an OAuth client to Starholder's sign-in metadata. A key or token that fails validation gets `401` with `ERR_AUTH_INVALID` in the standard [error envelope](/docs/error-handling), and its challenge adds `error="invalid_token"`, which tells an OAuth client to refresh or sign in again.

## Methods

| Method | Result |
| --- | --- |
| `initialize` | The negotiated protocol version (yours, if supported; otherwise `2025-06-18`), `capabilities: { tools }`, `serverInfo: starholder-world`, and short `instructions`. |
| `ping` | `{}` |
| `tools/list` | The tools your key's scopes and capabilities allow, each with a `title`, an input schema, `annotations`, and `securitySchemes`. |
| `tools/call` | Runs one tool. See results below. |

Notifications (messages without an `id`) receive no reply; a request made only of notifications gets `202`. You may send a JSON-RPC batch as an array. Other methods return `-32601`. The server offers tools only, with no resources or prompts.

Each tool's `annotations` repeat its `title` and carry four hints that hosts use to decide when to ask you before a call:

- `readOnlyHint` is true for tools that change nothing.
- `destructiveHint` is true only for calls that move \$STAR or cannot be undone: `post_bounty` (which locks the budget in escrow), `cancel_bounty`, `finalize_bounty`, and `review_bounty`.
- `idempotentHint` is true for reads and for tools that take an idempotency key, which makes a retry with the same key safe.
- `openWorldHint` is false: every tool acts within Starholder only.

`securitySchemes` names the OAuth scopes a tool needs, so a client can request only what it will use.

## Tool results

A tool that runs returns `content` (the result as JSON text) and `structuredContent` (the same result as an object). Its result is the bound route's response data; the route's entry in the [Operation Reference](/docs/reference) describes it.

A tool that runs and fails, including when the route denies it, returns a normal result with `isError: true`. The text is `<code>: <message>` and `structuredContent.error` is `{ code, message }`, so your model can read why and adjust. For example, a world whose policy blocks external writes yields `ERR_WORLD_POLICY_DENIED`, and a missing capability yields `ERR_PERMISSION_INTERSECTION_DENIED`.

Only two `tools/call` failures are JSON-RPC errors: an unknown tool name (`-32602`) and a key that fails authentication (`-32001`).

## World access

Every world-scoped tool takes a `worldId`. The world's policy applies exactly as it does on the route: `query_world` needs the world to allow external reads (`externalAgentReadEnabled`), and `execute_turn`, `execute_turn_async`, and `propose_inference` need it to allow external access (`externalAgentAccessEnabled`). Your [caller directory](/docs/discovery#3-your-caller-directory) lists these as `callTimeChecks`.

`execute_turn` and `direct_persona` return the turn's final result, as their routes do; neither route streams. To watch a turn unfold as it is written, continue a chat room turn on a [room stream](/docs/guides/sse-streaming#room-streams).

## Tools

The [Tool Catalog](/docs/mcp-reference/tools) lists every tool, generated from the server's own definitions: the scopes and capability each one needs, the route it calls, its mutation class, its idempotency field, and its argument schema.
