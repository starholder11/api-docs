## huelva_ask_or_followthrough

`POST /api/v1/huelva`

**Ask Huelva without a room.** Huelva's headless entry (AES §8.4.9). Runs one Huelva ask for the caller's owner with the API key or OAuth connection alone: a free-text user_message, or a structured follow-through on a known proposal, plan, or outcome. With worldId the ask is anchored on the owner's latest open non-room session in that world; without it Huelva works from her home advisory session. Either way she works across every world the owner owns or is a member of. Asking changes nothing in a world: an ask runs no staged work, including work Huelva would run at once in the app and an approval said in words. One staged action comes back as responseKind 'proposal' with a confirm action whose approveBody and rejectBody are this operation's own proposal_followthrough bodies; several come back as a plan in shell.result (kind 'plan', plan.planId), decided with a plan_followthrough body. shell.result.kind also tells an answer (resolution, whose citations carry the sourceRefs she relied on) from a clarification, a question the next user_message answers, and from honest_insufficiency. Name a world in userMessage by its handle (@owner/world) or send worldId; asks on the same anchor share its recent exchanges. The body is validated before authorization because huelvaAsk.kind names the policy: a user_message is authorized against huelva_ask (world:read, inference:propose), and every follow-through kind against huelva_followthrough, which also needs world:write. The confirm result is reported in fields: responseKind 'rejected' for a rejection, 'approval_status' for every other outcome (resolutionState, executionBridged, receiptRefs, failure), each with the world the proposal was staged for. Steps that run in the Starholder app (client settlements) are reported in shell.result, and responseText says so; nothing claims the caller carried them out. The same room-lane reply fields as chat_room_addons_huelva_ask_post. A user_message with a requestId that already committed replays the stored answer. A buffered call may run for minutes (maxDuration 800s); with Accept: text/event-stream the response becomes an SSE stream with a 770s run budget.

**Credentials.** Any one of: `X-Api-Key: <apiKey>`; `Authorization: Bearer <apiKey>`. Accepts an API key (X-Api-Key, or Authorization: Bearer; when both are sent, Authorization is used). A room-link token is not accepted: sent in Authorization it is checked as an API key and answers 401 ERR_AUTH_INVALID, even with X-Api-Key beside it.

**Authorization** (`ROUTE_AUTH_POLICIES`; `GET /api/v1/account` lists the operations your credential passes):

- `huelva_ask`: callers `external_agent`; scopes `world:read`, `inference:propose`; mutation class `none`.
- `huelva_followthrough`: callers `external_agent`; scopes `world:read`, `inference:propose`, `world:write`; mutation class `none`.

**Server-sent events**

Accept header contains 'text/event-stream'. Input validation, authorization, the origin header, quota, and the world check answer first as plain HTTP responses; once they pass, the stream opens and every outcome (including Huelva's 400, 409, 502, and 504) is delivered in the terminal 'settled' event while the HTTP status is 200. Content-Type: text/event-stream; charset=utf-8; Cache-Control: no-cache, no-transform; X-Accel-Buffering: no.

| Event | Data |
| --- | --- |
| `(comment)` | Initial ': ok' comment; then ': huelva-ask-keepalive' comment every 10s before each ping. |
| `open` | Sent immediately. |
| `ping` | Every 10s. |
| `progress` | Advisory research-loop progress. ([`HuelvaPrototypeProgressNotice`](/docs/reference/schemas#huelvaprototypeprogressnotice)) |
| `settled` | Terminal. The exact HTTP status and JSON body the buffered transport would have returned. The stream then closes. |

**Resume:** None. No SSE id fields are emitted and Last-Event-ID is not read. A reconnect re-POSTs a new ask.
